The shift

From autocomplete to agents

In a few short years, the unit of help went from a token, to a turn, to a whole task.

~2021

Autocomplete

Predicts the next few lines. You drive everything else.

→
~2023

Chat assistants

Ask & paste. Good answers, you wire them in by hand.

→
2025–26

Coding agents

Read the repo, plan, edit many files, run commands, verify, iterate.

The agent now owns the loop, not just the keystroke, which is why how you direct it matters more than how fast you type.

The key transition is the third box: the model went from suggesting to acting and verifying. Our job shifts from typing code to directing an agent and reviewing its work.
The mental model

Everything is one loop

Every good outcome comes from closing this loop, and the biggest lever is giving the agent a way to check its own work.

01

Gather context

Files, docs, tickets, errors

→
02

Act

Edit code, run commands

→
03

Verify

Tests, build, lint, screenshot

→
04

Iterate

Read failures, fix, repeat

The single highest-leverage move: give it something to verify against, tests, a build, a type-checker, a screenshot to diff. Then the loop closes on its own.

If you take one slide away, it's this. "Looks done" is a weak signal; "tests pass" is a strong one. When the agent can verify, it self-corrects instead of handing you broken code.
The operating principle

Context is your budget

The context window is finite, and quality degrades as it fills. Managing it is the skill that separates "meh" from "magic."

The core workflow

Explore → Plan → Code → Commit

For anything non-trivial, separate understanding from doing. It stops the agent from confidently solving the wrong problem.

→

For a one-line change, skip to code. For anything you'd struggle to describe in a sentence, plan first. Rewind means you can let it try risky things safely.

Claude Code · memory

Memory persists, context does not

Context is the live working window for one session. Memory is the small set of files reloaded at the start of every session.

MEMORY CLAUDE.md (you write it) · MEMORY.md (Claude updates it as it learns)
reloaded at the start of every session

Session 1

context fills, then you /clear

Session 2

fresh window, same memory

Session 3

starts smarter each time

Context is per session and disposable. Memory is small, persistent, and worth curating, because every future session reads it.

The distinction people miss: clearing context does not lose your project knowledge. That lives in memory and reloads next time. Keep CLAUDE.md tight and let MEMORY.md collect the hard-won lessons.

Claude Code · skills

Skills: package a workflow once

A skill is a small folder Claude loads only when it is relevant, so your team's know-how is reusable without sitting in context all the time.

Anatomy

A SKILL.md with frontmatter and instructions, plus optional scripts, templates, and reference files.

Loaded on demand

Only the short description stays in context. The full skill loads when the task matches, so the window stays lean.

Two ways to fire

Type /the-skill yourself, or let Claude invoke it automatically by context.

.claude/skills/deploy-staging/ 
deploy-staging/
├─ SKILL.md          frontmatter + steps
├─ scripts/
│  └─ smoke-test.sh
└─ templates/
   └─ release-notes.md

Share across the team in git, or bundle several into a plugin.

Good skills to write first: deploys, release checklists, codegen patterns, review rubrics, and onboarding.

The pitch: anything you explain to a new hire more than once is a candidate for a skill. Progressive loading is the key idea, dozens of skills cost almost nothing until one is actually needed.
Claude Code · skills

Progressive loading, two flavors

You can keep dozens of skills around. Only their short descriptions sit in context until one is actually used.

Progressive loading, pay only for what you use
Always · tiny

Name + description

A few tokens. The model reads this to decide if the skill is relevant.

→
On match

SKILL.md body

The full instructions load only when the task fits.

→
On demand

Scripts, templates, files

Read or run only when needed. A script can run without its source entering context.

Stateless · prefer

A self-contained recipe

Same input, same result, no side effects. Easy to share, test, and trust. For example: format a commit, scaffold from a template, run a checklist.

Stateful · with care

Touches state outside the run

Reads or writes files, a database, or a tracker, or carries progress across steps. Make side effects explicit, guard them with permissions, and keep them idempotent. For example: deploy, update a changelog, sync issues.

Progressive loading is why a big skill library is cheap, you only pay for the one in use. On state: reach for stateless by default, it is predictable and testable. When a skill must be stateful, make the side effects loud and gate them.
Make it deterministic

Hooks: automate the guardrails

Run a script on lifecycle events, so the right thing happens every time, not just when the model remembers to.

PostToolUse

Auto-format or lint after every edit.

PreToolUse

Block dangerous commands before they run.

Stop / SessionStart

Audit logs, notifications, env setup.

.claude/settings.json 
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "prettier --write $FILE_PATH"
      }]
    }]
  }
}
Hooks turn "please remember to format" into a guarantee. Deterministic guardrails are what make agents safe to run with looser permissions.

Stay in control

Permissions & safety

Tune how much Claude can do without asking, cut friction on safe actions, hard-block the dangerous ones.

Modes, cycle with ⇧Tab

Plan

Read-only exploration.

Default → Auto-accept edits

Prompt for each, or auto-approve edits.

Auto

Classifier approves routine work, blocks escalation.

.claude/settings.json 
{
  "permissions": {
    "allow": ["Bash(pnpm test)", "Bash(git commit *)"],
    "ask":   ["Edit(package.json)"],
    "deny":  ["Bash(rm -rf *)"]
  }
}

Evaluated deny → ask → allow. Add an OS-level sandbox for defense-in-depth.

Sweet spot: allowlist the safe, repetitive commands so you stop clicking "yes," and deny the destructive ones. Bypass mode is for isolated containers only.

Right tool, right moment

Tab vs ⌘K vs Agent

Reach for the smallest tool that fits, it keeps you in flow and keeps the diff reviewable.

Tab: in flow

Multi-line, next-edit prediction, auto-imports, jump-to-next-edit. Best while you're actively typing.

Tab to accept

⌘K: one spot

A focused change to a known selection, or a quick question about it. Single-file, surgical.

⌘K on a selection

Agent: the task

Multi-file features & refactors. Searches the repo, edits, runs commands, even drives a browser.

⌘L to open

Not sure which files matter? Skip the @-mentions, Agent will search and find them itself.

The skill is escalation: stay on Tab while typing, pop ⌘K for a known tweak, only open the Agent for genuinely multi-file work.

Highest-leverage team setup

Rules: shared instructions for the agent

Version-controlled guidance the agent follows every time, Cursor's equivalent of CLAUDE.md.

.cursor/rules/*.mdc

Project rules, scoped by glob or applied always.

AGENTS.md

Plain-markdown alternative; nest one per directory.

User & Team rules

Personal prefs, org-wide standards from the dashboard.

Prefer small, glob-scoped rules over one giant always-on file.

.cursor/rules/components.mdc 
---
description: React component standards
globs: src/**/*.tsx
alwaysApply: false
---
- Function components + hooks only.
- Co-locate styles; no inline style props.
- Every component gets a *.test.tsx.
Note the convergence: both tools settle on committed, scoped instruction files (AGENTS.md is becoming a cross-tool convention). Glob-scoping keeps prompts lean.

Work that runs without you

Cloud Agents & Bugbot

Cloud (background) agents

Autonomous agents in isolated cloud VMs, they build, test, drive a browser, and open merge-ready PRs with screenshots & logs.

@cursor in Slack GitHub / Linear Web & mobile

A backlog item can become a draft PR before you sit down.

Bugbot, AI code review

Reviews every PR diff and leaves inline comments with fixes, regressions, missing error handling, security issues, on human and agent-authored PRs.

Treat agent output like a junior dev's PR: always review & gate on CI.

Where "agents at scale" gets real — and why automated review matters: when agents open PRs, you need an agent helping review them, plus a human owning the merge.

Quality · the risk

Watch for AI slop

Over-engineering

Needless layers and config.

Reinvented wheels

Duplicates code you already have.

Plausible but wrong

Compiles and reads well, wrong logic.

Invented APIs

Calls things that do not exist.

Unreviewable diffs

Too big for anyone to actually read.

Off house-style

Ignores conventions, leaves dead code.

Why every item on the left needs a human who still understands the change.

Slop is not a model problem you wait out, it is a direction-and-review problem you manage. Karpathy's point is the whole game, you can hand off the typing but not the understanding.

How to keep it clean

Steer it, before it writes

Point at a pattern

Smallest change that works

One concern per task. Resist refactoring the world.

Gate it, before you merge

Tests, types, lint, and build. Wrong code should fail loudly.

Read the diff like a PR

You own the merge. Skim-and-approve is how slop ships.

Run the reviewers

/code-review and /security-review, or Cursor's Bugbot.

The fix is not less AI. It is tighter direction up front and honest review at the end.

Tie it back to the loop: a hard verifier plus a real review is what turns a fast draft into something you trust in main.
